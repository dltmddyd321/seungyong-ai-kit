# 지원 서류·면접 준비 규칙

이력서, 경력기술서, 자기소개서, 포트폴리오, 면접 답변처럼 사용자 이름으로 제출하는 글을 AI 에이전트와 다듬을 때 쓰는 규칙이다.

## 1. AI가 쓴 티가 나면 안 된다

요청마다 말하지 않아도 항상 적용한다. 한 줄을 고칠 때도 적용하고, 새로 쓴 문장은 넣기 전에 다시 읽고 다듬는다.

**피할 것**
- "~부터 ~까지 직접 결정하고 책임지는" 같은 상투적 포장
- 같은 종결 틀 반복("~하도록 처리", "~할 수 있습니다" 연속)
- 볼드 남발, "**굵은 제목:** 설명" 형식. 한 문장으로 풀어 쓴다.
- "~이 핵심입니다"류 결론 문장, 대구와 경구체
- 향상, 제고, 완성도 같은 추상 명사로 끝나는 문장
- 괄호 병기와 측정 조건 괄호 남발. 문장으로 푼다.
- 단어를 잇는 중앙점(·). "와/과"나 쉼표로 바꾼다.
- 화살표(→)로 이은 서술. 문장으로 바꾼다.

**원칙**
- 사실과 수치는 바꾸지 않고 문장만 고친다.
- 사실만 쓴다. 동기나 판단 이유를 추론해서 넣지 않는다.
- 긴 글(자기소개, 블로그)은 한국어 윤문 스킬(예: `humanize-korean`)로 마무리한다. 불릿 단위 이력서 문장은 직접 다듬는다.

**Why:** "AI가 쓴 티가 나면 안 된다, 항상 인지하라"는 지시를 받았다. 채용 담당자가 AI 티로 꼽는 패턴(위 목록)이 서류 탈락 원인으로 의심된 적도 있다.

## 2. 사용자 제안이라도 관례에 안 맞으면 반대한다

사용자가 제안한 내용이라도 업계 관례나 서류 작성 원칙에 맞지 않으면 그대로 반영하지 않는다. 첫 문장에서 "이건 권하지 않습니다"라고 분명히 말하고 근거와 대안을 제시한다.

- 제안을 받으면 먼저 관례(멘토나 회사가 준 양식, 채용 담당자 관점, 3초 안에 훑어지는지, 사실 검증이 가능한지)와 대조한다.
- 맞으면 반영하고, 안 맞으면 반영하지 않은 채 이유와 대안을 말한다.
- "~가 좋지 않아?" 같은 질문 형태의 제안도 같은 기준으로 본다.

**Why:** 포트폴리오 본문을 존댓말로 바꾸자는 질문에 바로 따랐는데, 포트폴리오는 문제, 해결, 결과를 개조식으로 쓰는 게 관례라 반대했어야 했다. 이후 "통상적으로 안 맞는 부분은 확실하게 거절하라"는 지시를 받았다.

## 3. 사용자의 기술 설명이 틀리면 첫 문장에서 지적한다

`rules/working-style.md` 4번과 같다. 서류나 면접 답변에 들어갈 내용이면 틀린 표현이 왜 위험한지(예상 꼬리질문) 한 줄 덧붙인다.

## 4. 면접관은 회사 코드를 볼 수 없다

면접 준비는 면접관이 보안 정책상 지원자 회사의 코드를 볼 수 없다는 전제로 돕는다.

- 예상 질문 대비는 "왜 그렇게 설계했나, 대안과 트레이드오프" 중심으로 원리 수준 설명을 준비하게 한다.
- 코드 확인은 사용자 설명이 사실과 어긋나지 않게 하는 용도로만 제안한다. 클래스명이나 내부 구현을 그대로 말하도록 유도하지 않는다.

**Why:** "코드로 확인해 둘 것" 위주로 준비 항목을 적었다가 지적받았다. 회사 코드를 외부에 노출하지 않는 원칙(`writing/tech-blog.md` 1번)과 같은 맥락이다.

## 5. 서류를 고치면 면접 노트도 같은 턴에 고친다

경력기술서나 포트폴리오에 문장을 추가하거나 고치면, 같은 회사 폴더의 기술면접 노트(예: `career/<회사>/interview_prep.md`)에도 그 문장의 사실 근거(git, 코드 확인)와 예상 꼬리질문을 함께 반영한다.

- 서류 수정이 끝날 때 노트의 수치 출처 표, 서류 문장과 노트 위치의 대응 표, 해당 사례 꼬리질문을 같이 갱신한다.
- 보고할 때 노트에 무엇을 넣었는지 함께 말한다.

**Why:** 서류에 들어간 문장은 전부 면접 꼬리질문 대상이다. 노트가 뒤처지면 면접 준비에 구멍이 생긴다.

## 6. 문서 파일 관리

- 회사별 폴더로 서류와 면접 노트를 나눠 관리한다.
- 수정할 때 `.backup_*` 같은 복사본을 만들지 않는다. 원본만 최신화하고, PDF가 있으면 수정 후 다시 만든다(`rules/working-style.md` 11번).
