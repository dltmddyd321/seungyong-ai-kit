# 기술 블로그 작성 규칙

개인 기술 블로그 글을 AI 에이전트와 함께 쓸 때 쓰는 규칙이다. 블로그 저장소의 `AGENTS.md`(+ `CLAUDE.md`)에 넣어 두면 어느 기기에서 작업하든 같은 규칙이 적용된다.

## 1. 회사 코드 기밀 유지

회사 업무를 소재로 글을 쓸 때 실제 코드나 로직을 그대로든 살짝 바꿔서든 재현하지 않는다. 항상 의사코드로 추상화하거나, 실제 구현이 역추적되지 않도록 이름과 구조를 충분히 바꾼다.

**Why:** 회사 코드의 중요한 기술 내용이 외부로 새면 안 된다. 스타일 취향이 아니라 기밀 경계선이라 예외 없이 지킨다. "실제 코드로 보여 주는 게 더 잘 설명된다"는 이유도 예외가 아니다.

**적용 방법**
- 쓰기 전에 다음이 들어 있는지 확인한다: 실제 클래스/함수/변수명, 정확한 비즈니스 로직이나 알고리즘, 실제 API 엔드포인트나 요청/응답 형태, 회사 저장소에서 가져온 코드 블록(일부라도).
- 구체적인 식별자는 일반화된 이름으로 바꾼다. 예: 실제 테마 클래스 → `ThemeManager`/`ThemeResolver`, 실제 엔드포인트 → `/api/theme/attributes` 같은 범용 예시.
- 정확한 구현을 재현하기보다 문제의 형태와 디버깅/설계 방법을 이야기한다. 예: "기기에 캐시된 DB를 직접 조회해서 원인을 증명했다", "로컬 기본값이 없는 이미지 필드가 회전 시 null로 떨어졌다".
- 실제 패키지명, 파일 경로와 파일명, 라이브러리 버전 숫자, 이슈 트래커 링크, 앱 버전도 그대로 쓰지 않는다.
- 회사 프로젝트에 도구를 써 본 과정을 설명할 때도 발견 사실은 카테고리 수준으로 뭉뚱그린다. 예: "버전 정보 몇 개가 실제 코드보다 뒤처져 있었다"는 괜찮고, 구체적인 라이브러리 버전 변경 내역은 쓰지 않는다.
- 어느 프로젝트 세션에서 글을 쓰든 똑같이 적용된다. 이 규칙은 저장소가 아니라 "회사 관련 소재를 다루는 글"이라는 주제에 붙는다.

## 2. 문체: 존댓말, 담백하게, AI 티 없이

**존댓말만 쓴다.** 모든 문장을 `-습니다/-입니다`체로 끝낸다. 평어체(`-다` 종결)를 섞지 않는다.

**Why:** 같은 날 올린 두 글의 문체가 서로 달랐던 적이 있다.

**AI가 쓴 티가 나면 안 된다.** 초안을 쓴 뒤 한국어 윤문 스킬(예: `humanize-korean`)로 다듬는다. 잘 쓴 초안은 보수적인 강도로 충분하고, 스킬에 변경률 점검이 있으면 꼭 돌린다. 평어체를 존댓말로 바꾸는 격식 전환은 윤문 스킬이 하지 않으므로 직접 고친다.

**처음부터 이렇게 쓴다** (사용자가 직접 손본 방향)
- 도입부는 담백한 상황 서술에 "기록해봅니다" 정도로 짧게. 극적인 훅을 만들지 않는다.
- `1차 시도/2차 시도` 같은 번호 서사를 쓰지 않고, 헤딩에도 번호를 붙이지 않는다.
- Bottom Sheet, Navigation Bar, Status Bar처럼 영어 기술 용어는 억지로 한글화하지 않는다.
- 한 문장씩 줄바꿈하는 짧은 줄 단위 문단으로 쓴다.
- 마지막 "정리"는 리드인 문장 없이 불릿만 둔다. 본문 구조를 그대로 되풀이하지 않는다.
- 핵심 원인 규명에 기여하지 않는 곁가지 에피소드는 통째로 뺀다.
- 코드나 명령어 블록 앞은 "쓴 명령은 두 개입니다."처럼 딱 끊어 선언하지 말고, "아래 명령어 두 개를 사용해서 확인 가능합니다."처럼 뒤 내용으로 자연스럽게 잇는다.
- 무슨 이야기를 할지 예고하는 대신 그냥 그 이야기를 한다.

**피할 습관** (윤문 진단에서 반복 지적된 것)
- 산문에 볼드 남발, 특히 `**N번째 —**` 같은 리드인 템플릿 반복
- `라벨: 부제` 형태의 콜론 헤딩을 여러 개 만들어 대칭 구조 만들기(문서당 1회 정도까지)
- "측정만이 가설을 죽입니다" 같은 대구 경구체 결말
- 따옴표 강조 남발(문서당 5회 이하)
- `~셈입니다` 결론 어미 반복. 다른 종결이나 그냥 서술로 분산한다.
- 문장 길이와 종결어미가 모두 비슷해지는 것. 존댓말 안에서도 `-습니다/-입니다/-였습니다/-합니다`로 분산한다.

## 3. 도구 소개 글은 시행착오보다 결과물

기술이나 도구를 소개하는 글에는 만들면서 겪은 버그, 실행 주기를 바꾼 과정, 직접 정한 판단 규칙 같은 절차와 시행착오를 넣지 않는다. 기술의 정의와 사용법, 그것으로 만든 결과물에 집중한다.

- 결과물 섹션 순서: 무엇을 해 주는가 → 어떤 도구를 거치는가(표/구조도) → 결과 예시 → 무엇이 줄었나
- 디버깅 과정 자체가 주제인 글(디버깅 후기)은 예외다.

**Why:** "버그 N개", "30분마다 → 요청할 때만" 같은 섹션을 보고 "결국 이 기술로 만든 결과물이 중요하고, 내가 자체적으로 고민한 비즈니스 로직은 이 글에 맞지 않다"는 지적을 받았다.

## 4. 애니메이션·인터랙션을 다루는 글엔 상태 변화 GIF

드래그, 전환 애니메이션, 제스처처럼 시간에 따라 화면이 변하는 동작을 설명하는 글에는 변하는 상태를 보여 주는 GIF를 직접 만들어 넣는다. 기존 동작과 바꾼 동작을 비교할 수 있으면 두 장으로 나눈다.

- 회사 소재라면 실제 앱 화면 녹화 대신 원리만 보여 주는 추상화된 GIF를 코드로 그린다. 카드는 회색 줄 같은 placeholder로, 라벨은 날짜나 진행률 같은 설명용만 둔다. 1번 기밀 규칙과 같은 기준이다.
- 글의 의사코드와 같은 수치와 규칙(진행률, 임계값 등)으로 그려서 글과 GIF가 어긋나지 않게 한다.
- 본문에는 무엇이 보이는지 설명하는 alt 텍스트와 함께 넣는다. 파일명은 `<timestamp>-<name>.gif`처럼 충돌하지 않게 짓는다.

**Why:** 정지 스크린샷이나 글만으로는 "중간에 멈춘다", "놓으면 이어서 넘어간다" 같은 차이가 전달되지 않는다.

## 5. 스크린샷은 민감 정보를 가리고 넣는다

앱 스크린샷을 넣을 때는 사용자 이름, 프로필 사진, 계정 정보, 개발 빌드나 버전 표시처럼 드러나면 안 되는 부분을 가린다. 설명에 필요한 영역만 잘라내는 방식이 가장 깔끔하다(가릴 정보가 처음부터 안 들어간다). 강조할 영역은 빨간 점선 같은 표시로 짚는다.

**Why:** 스크린샷이 있으면 글이 더 잘 읽히지만, 1번 기밀 규칙과 같은 이유로 노출 범위를 줄여야 한다.

## 6. AI 요약 필드가 있는 블로그라면

글 상단에 AI 요약 배너(예: frontmatter의 `aiPreview` 필드)를 쓰는 블로그라면:

- 모든 글에 넣는다. 사용자가 직접 쓴 글도 포함해서, 요청을 기다리지 않고 에이전트가 글을 읽고 채운다. 작업할 때마다 이 필드가 빠진 글이 있는지 확인한다.
- `description`을 바꿔 쓰지 말고 글을 읽고 실제 내용을 요약한다.
- 스키마에서는 선택 항목으로 둔다. 필수로 바꾸면 사용자가 웹 편집기로 바로 발행할 때 빌드가 실패해 배포가 막힌다.
- "핵심만 보면 —", "요약하면", "정리하자면" 같은 말머리 없이 바로 본론으로 시작한다.

**Why:** 원래 "에이전트가 쓴 글에만 붙이는 필드"로 정했더니 사용자가 직접 쓴 글에 배너가 빠졌다. 또 배너에 이미 "AI Preview" 라벨이 있어서 말머리는 라벨을 한 번 더 말하는 셈이고, 모든 글에 같은 문구가 반복되면 템플릿처럼 읽혔다.

## 7. 저자 이름 표기

- 한글 이름: 조사(`의`, `는`)나 어미(`입니다`)가 붙는 문장 안. 메타 설명, 소개 문장 등.
- 영문 이름: 문장의 일부가 아닌 독립 라벨. 사이트 로고, 푸터 저작권, 프로필 이름, meta `author`.
- schema.org JSON-LD는 `name`에 영문, `alternateName`에 한글을 둬서 양쪽을 유지한다.

**Why:** 사이트 전체를 영문 이름으로 바꿨더니 "…개발자, GildongHong입니다."처럼 한글 문장 안에서 어색하게 읽혔다.

## 8. 발행

블로그 저장소에서 "작업 완료 = 커밋과 푸시까지"로 정했다면 `rules/git-commit.md` 5, 6번을 따른다.

- 빌드가 통과하면 초안 컨펌 없이 바로 게시하고, 배포 완료까지 확인해서 알린다. 사용자는 발행 후 직접 고치는 쪽이 편하다고 했다.
- `git add`는 해당 글과 그 글이 쓰는 업로드 파일만 한다.
- 커밋 메시지는 저장소 컨벤션을 따른다. 예: 새 글과 글 수정은 `post: <제목 또는 변경 요약>`.
- 원격이 앞서 있어 푸시가 거절되면 force push 하지 않고, fetch 후 원격 diff를 읽고 rebase한다.
