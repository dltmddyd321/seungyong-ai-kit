# 보안·배포 점검 규칙

두 규칙 모두 "직접 실행하지 말고 제안만" 한다. 실행은 사용자가 승인한 뒤에 한다.

## 1. 보안 경계에 닿는 작업이면 범위를 좁힌 보안 감사를 제안한다

보안 경계에 닿는 작업을 끝냈으면, 보안 감사 스킬(예: `security-audit`)로 범위를 좁힌 감사를 돌릴지 먼저 제안한다.

**Why:** 사용자가 "중요한 작업이면 판단해서 제안해 달라"고 요청했다. 전체 감사는 에이전트를 여러 개 띄워 토큰 비용이 커서 자동으로 실행하지 않는다.

**제안 대상**
- 딥링크, App Link, intent 처리
- exported 컴포넌트, PendingIntent
- WebView
- 인증 토큰, 로그인, 세션
- 결제, 구독
- 서버 API 인증·헤더
- 서명·빌드 설정(`signingConfig`, `debuggable`). 예: debug 빌드가 release 키로 서명되고 `debuggable`이며 `applicationId` 접미사가 없으면, 유출됐을 때 운영 앱 위에 설치될 수 있다.
- 파일 처리, 공유 처리
- 외부 입력 파싱

**제안하지 않는 것**
- 순수 UI, 문구, 색상, 레이아웃
- 내부 로직 리팩터링

**제안 방식**
- 한두 줄로 쓴다. 왜 필요한지, 좁힌 범위(예: "이번 초대 링크 처리 경로만"), 비용을 함께 말한다.

## 2. 빌드 업로드·배포 전에는 난독화 점검을 제안한다

사용자가 빌드 업로드나 배포를 하려는 게 보이면 직접 실행하지 말고 `release-obfuscation-check` 스킬의 R8/Gson 점검을 먼저 하자고 제안한다.

**Why:** 난독화 문제는 release 빌드에서만 드러나고, Gson으로 직렬화하던 클래스가 난독화되어 release에서만 크래시가 난 사례가 있다. 점검 항목과 배경은 `skills/release-obfuscation-check/SKILL.md`에 있다.
