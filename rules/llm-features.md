# 앱에 LLM 기능을 넣을 때

앱에서 외부 LLM API(Gemini, Claude, OpenAI 등)를 호출하는 기능을 만들 때 쓰는 규칙이다.

## 1. 배포 바이너리에 API 키를 넣지 않는다

앱 바이너리에 들어간 키(`BuildConfig`, 리소스, 상수)는 디컴파일로 그대로 꺼낼 수 있다. 배포용 빌드는 키 없이 만들고, 키가 없으면 그 기능만 꺼지게 한다(앱 전체가 죽지 않게).

- 배포 산출물을 만든 뒤 키 필드가 비었는지 확인한다. 값을 출력하지 말고 길이만 본다.
- 결제가 연결된 키가 새면 남이 쓴 만큼 청구된다. 실서비스는 서버를 거쳐 호출하는 구조로 간다.
- 키는 URL 쿼리가 아니라 헤더로 보낸다. 쿼리는 로그와 프록시에 남는다.

**Why:** 개인 프로젝트 APK를 테스터에게 배포하면서 키를 빼고 빌드했다. 키를 넣은 채 배포했다면 누구나 꺼내 쓸 수 있었다.

## 2. 실패 종류별로 다르게 처리하고, 폴백 모델의 파라미터 호환을 확인한다

| 응답 | 처리 |
|---|---|
| 503, 429, 500 | 다음 폴백 모델로 넘어간다 |
| 401, 403 | 키 문제다. 폴백하지 않고 바로 안내한다 |
| 그 밖의 4xx | 요청 자체가 틀렸다. 같은 요청을 반복하지 않는다 |

- 폴백 목록의 모델마다 같은 요청 파라미터를 받는지 직접 호출해서 확인한다. 같은 회사 모델이라도 세대마다 받는 설정이 다르다.

**Why:** 사고 수준 설정(`thinkingLevel`)을 최신 모델에 맞춰 넣었더니 폴백 대상인 이전 세대 모델이 400을 돌려줬다. 세 모델이 모두 받는 다른 설정(`thinkingBudget`)으로 바꿨다.

## 3. 상위 모델로 바꾸기 전에 측정한다

"유료나 상위 모델이면 더 좋아지겠지"로 결정하지 않는다. 같은 입력으로 응답 시간, 출력 토큰 수, 결과 품질을 모델별로 재고 나서 고른다.

- 추론(thinking) 토큰도 출력 토큰으로 과금된다. 답이 짧은 작업에서는 추론 토큰이 비용 대부분을 차지할 수 있다.
- 무료 등급에서는 상위 모델 할당량이 0인 경우가 있다. 실제로 호출해 본다.

**Why:** 측정해 보니 답은 수백 토큰인데 추론 토큰이 1,300~1,500개였다. 추론을 끄자 응답이 19~20초에서 6~14초로 줄고 출력 비용이 약 65% 줄었다. 결과 품질은 차이가 없었다. 상위 모델은 무료 등급 할당량이 0이라 아예 호출되지 않았다.

## 4. 실제로 나가는 요청을 출력해 확인한다

요청 객체를 코드로 조립했다고 그대로 나간다고 믿지 않는다. 직렬화된 요청 문자열을 한 번 출력하거나 단위 테스트로 고정한다.

- 직렬화 라이브러리가 기본값과 같은 필드를 생략하는 설정(예: kotlinx.serialization의 `encodeDefaults = false`)이면 직접 넣은 설정이 통째로 빠질 수 있다. 기본값도 내보내고 null만 빼는 쪽(`encodeDefaults = true`, `explicitNulls = false`)이 안전하다.

**Why:** 추론을 끄는 설정을 넣었는데 효과가 없어서 요청을 출력해 보니 `"generationConfig":{}`로 비어 있었다. 기본값 생략 설정 때문이었다.

## 5. 모델이 볼 수 없는 제약은 프롬프트에 적는다

모델은 화면 크기, 에셋 비율, 겹치면 안 되는 UI 영역처럼 앱만 아는 제약을 모른다. 결과가 이런 제약에 걸리면 모델 탓을 하기 전에 프롬프트에 그 제약을 수치로 적는다.

**Why:** 인물 실루엣을 배치하는 기능에서 모델이 준 크기가 계속 작게 나왔다. 실루엣 에셋의 가로세로 비율을 프롬프트에 적고 나서 맞는 크기가 나왔다.

## 6. 할 수 없으면 "할 수 없다"고 답하게 한다

응답 형식에 "불가능" 경로를 둔다. 예: `{"suggestions": [], "unavailable": "사람이 설 자리가 없는 사진입니다"}`. 앱은 이 경우 억지 결과 대신 안내 문구를 보여 준다.

**Why:** 형식이 결과만 받게 되어 있으면 모델은 맞지 않는 입력에도 그럴듯한 값을 만들어 낸다. 사용자는 틀린 결과를 정상 결과로 받게 된다.
