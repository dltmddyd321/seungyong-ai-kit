# 에이전트 규칙 파일 운영

## 1. AGENTS.md가 원본, CLAUDE.md는 불러오기만

프로젝트 규칙 문서는 `AGENTS.md`를 단일 원본(SSOT)으로 둔다. `CLAUDE.md`는 첫 줄에 `@AGENTS.md` 한 줄만 적어 내용을 불러온다. Claude Code에만 해당하는 지시가 생기면 그 줄 아래에 덧붙이고, 전체를 복제하지 않는다.

```
@AGENTS.md
```

- 규칙, 코딩 스타일, 하네스 관련 내용을 고칠 때는 `CLAUDE.md`가 아니라 `AGENTS.md`를 고친다.
- 브랜치에 따라 `AGENTS.md`가 없을 수 있다. 그럴 때는 있는 브랜치에서 `git show <branch>:AGENTS.md`로 가져오거나, 현재 `CLAUDE.md` 내용을 기반으로 새로 만든다.
- 템플릿: `templates/AGENTS.md`, `templates/CLAUDE.md`

**Why:** Codex 등 다른 벤더 에이전트는 `CLAUDE.md`가 아니라 `AGENTS.md`를 읽는다. 처음에는 두 파일을 손으로 똑같이 유지했는데, Claude Code의 `@path` import 문법으로 `CLAUDE.md`를 한 줄로 바꾸면 동기화할 필요 자체가 없어진다.

두 파일을 따로 유지해야 하는 사정이 있으면 `hooks/check-claude-agents-sync.sh`로 어긋남을 감지한다.

## 2. 하네스 변경 이력을 남긴다

`AGENTS.md`의 하네스(스킬, 에이전트, 훅) 섹션 끝에 변경 이력 표를 두고, 구성을 바꿀 때마다 한 줄씩 추가한다.

| 날짜 | 변경 내용 | 대상 | 사유 |
|------|----------|------|------|

**Why:** 하네스는 실패를 겪으며 조금씩 바뀐다. "왜 이 규칙이 생겼는지"가 남아 있지 않으면 나중에 같은 실패를 다시 겪거나, 이유를 모른 채 규칙을 지우게 된다.

## 3. 프로젝트 지침보다 사용자의 명시적 정정이 우선

프로젝트 규칙 파일에 "모든 코드 변경은 파이프라인으로", "수정 후 self-verification loop 실행"처럼 적혀 있어도, 사용자가 나중에 명시적으로 정정한 지시(파이프라인은 큰 작업에만, 빌드는 요청할 때만 등)가 우선한다. 정정이 반복되면 규칙 파일 자체를 고친다.

**Why:** 규칙 파일과 실제 선호가 어긋난 상태로 남아 있어서, 파일만 보고 움직이면 같은 지적을 계속 받았다.
