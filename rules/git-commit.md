# Git·커밋 규칙

## 1. 작업이 끝날 때마다 커밋 메시지를 텍스트로 준다

작업 하나가 끝나면 답변 마지막에 커밋 메시지를 텍스트로 제공한다. 빠뜨리지 않는다. 실제 `git add`/`git commit`은 사용자가 명시적으로 요청하기 전까지 실행하지 않는다.

**Why:** 사용자가 커밋 메시지를 직접 쓰는 수고를 줄이되, 커밋 여부와 시점은 직접 정하기 위해서다.

## 2. 형식

저장소에 이미 정해진 컨벤션이 있으면 그것을 따른다(`git log --oneline`으로 확인). 따로 없으면 아래 형식을 기본으로 한다.

```
{이슈 링크} {이슈 제목}

- 주요 변경 1
- 주요 변경 2
- 주요 변경 3
```

- 이슈가 있으면 첫 줄은 이슈 링크와 제목이다. `.claude/current_issue.md`가 있으면 그 `commit_prefix` 값을 그대로 첫 줄로 고정한다(`commands/issue.md` 참고).
- 이슈가 없으면 `- ` 줄만 쓴다. 저장소가 Conventional Commits(`feat:`, `fix:`, `refactor:` 등)를 쓰면 그 형식을 따른다.
- 구현한 내용만 `- `로 시작하는 줄에 하나씩 적는다. 설명, 배경, 사유 문장은 넣지 않는다.

**Why:** 실제 저장소 커밋 이력이 이 형식이고, 본문이 장황해지는 것을 줄이기 위해 정했다.

## 3. 항상 하나만, 큰 단위만

- 커밋 메시지는 언제나 하나만 준다. 작업별로 나눈 대안 메시지를 덧붙이지 않는다.
- `- ` 줄은 큰 단위의 주요 변경만 3~5줄 정도로 추린다. 수치 조정 같은 자잘한 항목은 넣지 않는다.

**Why:** "커밋은 항상 한 번에, 주요 내용만"이라는 지시를 받았다.

## 4. 범위는 커밋되지 않은 변경 전체

커밋 메시지를 달라고 하면 직전 작업만이 아니라 그 시점에 커밋되지 않은 변경 전체(`git status`/`git diff` 기준, 사용자가 직접 고친 것 포함)를 보고 메시지를 만든다.

**Why:** 사용자는 쌓인 변경을 한 번에 커밋한다. 직전 작업만 반영하면 사용자가 직접 고친 부분이 메시지에서 빠진다.

## 5. 자동 커밋·푸시는 저장소별로 명시된 경우만

기본은 커밋하지 않는다. 사용자가 특정 저장소(개인 블로그, 개인 도구 등)에 대해 "작업 완료 = 커밋과 푸시까지"라고 정했다면 그 저장소에서만 묻지 않고 끝까지 진행하고, 그 결정은 해당 저장소 규칙 파일에 적는다.

- 그런 저장소에서도 `git add`는 이번 작업 파일과 그 작업이 쓰는 에셋만 한다. 무관한 untracked 파일(`_workspace/` 등)은 넣지 않는다.
- 사용자가 아직 검토 중인 미완성 작업이거나 "diff 먼저 보여 달라"고 했으면 예외다.

**Why:** 배포가 `main` 푸시로 이뤄지는 저장소에서 로컬에만 있는 변경이 라이브에 없어 혼란이 생긴 적이 있다. 반대로 회사 저장소에서는 커밋 시점을 사용자가 정한다.

## 6. force push 금지

푸시가 거절되면 force push 하지 않는다. `git fetch` 후 원격 diff를 먼저 읽어 원격에 들어간 수정의 의도를 확인하고, 원격 기준으로 rebase해서 다시 올린다.

**Why:** 사용자가 웹 편집기 등으로 원격에서 직접 수정하는 경우가 있어, 원격이 로컬보다 앞서 있을 수 있다.
