# 작업 방식 규칙

AI 에이전트(Claude Code, Codex 등)와 일할 때 반복해서 정정한 내용을 규칙으로 정리했다.
각 규칙의 **Why**는 실제로 문제가 됐던 상황을 일반화한 것이다.

## 1. 응답은 한국어로만

사용자에게 보내는 모든 답변(분석 결과, 진행 상황 한 줄, 커밋 안내 포함)은 한국어로 쓴다. 코드 식별자, 로그, 커밋 메시지 원문만 예외다.

- 도구 호출 사이의 짧은 진행 메시지도 한국어로 쓴다.
- 도구를 여러 번 쓴 긴 분석 직후, 오래 기다린 뒤의 진행 보고, 영어로 된 서브에이전트 결과를 요약할 때 영어로 새기 쉽다. 이때 특히 확인한다.
- 답변을 보내기 전 영어 문장이 섞였는지 한 번 확인한다.

**Why:** 긴 작업의 중간 보고와 결과 보고가 영어로 나가서 여러 번 지적받았다.

## 2. AskUserQuestion에는 짧고 단순한 한글만

`AskUserQuestion`의 `question`/`option`/`preview` 필드에 길거나 화살표(→), 불릿(-), 줄바꿈이 섞인 한글을 넣으면 깨진 상태(유니코드 이스케이프가 텍스트로 노출되는 등)로 전달되는 경우가 있다.

- 질문이 짧고 단순할 때만 도구를 쓴다.
- 길거나, 여러 항목을 나열하거나, 표/화살표/줄바꿈이 필요하면 도구 대신 일반 채팅 텍스트로 묻는다.
- 꼭 써야 한다면 호출 전에 각 한글 문자열을 한 글자씩 다시 확인하고 `\uXXXX` 같은 이스케이프가 섞였는지 점검한다.
- 한 번 깨졌으면 같은 도구로 재시도하지 않고 바로 일반 텍스트로 전환한다.

**Why:** 깨진 질문이 실제로 전달됐고, 한 번이 아니라 반복 가능한 실패 패턴으로 확인됐다.

## 3. 정확성이 먼저, 추측 금지

- 판단하기 전에 실제 코드를 읽는다. 속도보다 정확성이 우선이다.
- "아마", "~일 것 같다"로 답하지 않는다. 코드, 커밋, 공식 문서로 확인한 내용만 말한다. 확인할 수 없으면 확인할 수 없다고 말한다.
- 변경 전 `grep`/Find Usages로 영향 범위를 넓게 확인한다. Java/Kotlin 혼용 프로젝트라면 교차 참조를 반드시 본다.
- 한 번에 하나만 고치고 확인한 뒤 다음으로 넘어간다.

**Why:** 추측으로 내린 판단이 틀렸을 때 되돌리는 비용이 처음부터 확인하는 비용보다 크다.

## 4. 사용자의 기술 설명이 틀리면 분명하게 지적

사용자가 말한 기술 설명, 원인 추정, 작업 기억이 코드나 문서와 다르면 첫 문장에서 "틀렸습니다"라고 판정하고 근거를 댄다. "~일 수도 있습니다"로 완곡하게 넘기지 않는다.

- 첫 문장에 판정(맞음/틀림/부분적으로 틀림)을 둔다.
- 코드, 커밋, 공식 문서로 근거를 보여 준다. 확인할 수 없으면 그렇다고 말하고 추측으로 판정하지 않는다.
- 이력서나 면접 답변에 들어갈 내용이면 틀린 표현이 왜 위험한지(꼬리질문) 한 줄 덧붙인다.

**Why:** 틀린 설명을 그대로 두면 면접이나 외부 발표에서 그대로 말하게 된다. 준비 단계에서 바로잡는 게 목적이다.

## 5. 요청하지 않은 주석은 쓰지 않는다

사용자가 그 요청에서 명시적으로 요구하지 않는 한 코드 주석을 추가하지 않는다. 짧은 "왜" 설명, 함수 위 KDoc 블록도 포함된다. 새 코드와 기존 코드 수정 모두 해당한다.

- 버그 원인, 플랫폼 특이사항, 워크어라운드 이유는 아무리 비직관적이어도 주석 대신 커밋 메시지나 채팅 답변으로 설명한다.
- 작업을 끝내기 전에 diff를 다시 훑어 습관적으로 들어간 주석이 있는지 확인하고, 있으면 지운다.

**Why:** 규칙이 있었는데도 버그 수정 중 설명 주석과 KDoc을 여러 번 습관적으로 넣었다. 코드와 커밋 메시지로 충분하다는 입장이고, "비직관적이니 남기는 게 낫다"는 예외로 인정하지 않는다.

## 6. 기존 정상 동작은 정책이다

기존 코드의 정상 동작은 서비스 정책과 연결돼 있다고 본다. 개선 작업 때문에 그 동작이 달라지거나 새 오류가 생기면 그 변경은 하지 않는다. 바꿔야 한다면 기존 구조는 두고 문제 지점만 고치는 최소 변경을 택한다.

- 리팩터링이나 신기술 전환(코루틴, Flow, Compose 등)을 제안하기 전에 기존 코드와 한 줄씩 대조해 동작 차이(실행 횟수, 반복 여부, 초기화 조건, 실행 스레드, 예외 처리)를 표로 먼저 확인한다.
- 차이가 하나라도 있으면 전환하지 않고, 기존 구조를 유지한 최소 수정안을 기본으로 제시한다.
- 전환이 더 낫다고 판단되면 동작 차이를 명시하고 승인받은 뒤에만 진행한다.
- 보고할 때 "기존과 같은 이유"를 항목별로 근거와 함께 적는다.

**Why:** 타이머 누수를 고치면서 `TimerTask`를 코루틴 `Job`으로 바꿨더니 재시도 횟수가 매번 초기화되고 시간 초과 감시가 반복 확인에서 1회 확인으로 바뀌었다. 결국 기존 `TimerTask`를 유지하고 종료 시점에 `cancel()`만 추가하는 방식으로 되돌렸다.

## 7. 빌드·설치는 요청할 때만

코드나 리소스를 수정한 뒤 compile, assemble, install, lint, test 같은 빌드 태스크(`./gradlew ...`, `xcodebuild`, 시뮬레이터/에뮬레이터 실행 등)를 스스로 실행하지 않는다. 사용자가 그 턴에서 "빌드해봐", "컴파일 확인해줘", "설치해줘"처럼 명시적으로 요청한 경우에만 실행한다.

- "버그를 고쳤으니 확인해 보자" 같은 선의도 예외가 아니다.
- 대신 Read/grep으로 정적 검증을 최대한 한다(import 누락, 타입 불일치, 참조 오타, XML well-formedness).
- 수정이 끝나면 "빌드는 확인 부탁드립니다" 정도로 마무리하고, 사용자가 고쳐 줄 만한 가정(스펙 해석 등)이 있으면 같이 적는다.
- 프로젝트 규칙 파일의 "Self-verification loop"보다 이 지시가 우선한다. 그 루프는 사용자가 요청했을 때만 돈다.
- 판단이 애매한 정적 태스크(예: 컴파일만)는 실행 전에 묻는다.

**Why:** 빌드와 설치는 시간이 오래 걸리고 토큰을 소모한다. 사용자는 빌드, 설치, 실기기 확인을 직접 하기로 했고, 규칙이 있는데도 검증 명목으로 반복 실행해 여러 번 정정했다.

## 8. 루프에서 실패하면 멈추고 보고

테스트나 빌드 검증 루프에서 실패가 나면 그 시점에 멈추고 보고한 뒤 수정 승인을 받는다. 승인 후 수정하고 처음부터 다시 실행한다. 혼자서 수정과 재실행을 반복하지 않는다.

- 보고에는 실패한 테스트/단계, 위치, 기대값과 실제값, 추정 원인(코드 문제인지 테스트 문제인지), 제안 수정안을 담는다.
- 승인 없이 다음 반복으로 넘어가지 않는다. 최대 반복 횟수는 안전장치일 뿐 자동 반복 허가가 아니다.
- 테스트를 통과시키려고 테스트 자체를 고치는 수정은 따로 명시해서 확인받는다.

**Why:** 자동 반복 루프는 토큰을 끝없이 소모하고, 사용자가 모르는 수정이 쌓인다.

## 9. 무거운 멀티 에이전트 파이프라인은 큰 작업에만

탐색→구현→빌드 검증→리뷰처럼 서브에이전트를 순차로 띄우는 파이프라인은 전체 알고리즘이 바뀌거나 파일이 크게 바뀌는 경우에만 쓴다. 나머지는 grep → Read → Edit로 직접 처리하고 결과만 보고한다.

- 애매하면 파이프라인보다 직접 처리 쪽으로 기운다.
- 파일 수가 많아도 사용자가 매핑이나 스펙을 이미 확정한 기계적 작업(확정된 토큰 값을 여러 뷰에 옮기는 것 등)이면 탐색 단계를 생략하고 직접 처리한다.
- 리뷰 단계는 기본 생략하고, 치명적 위험이 강하게 의심될 때만 돌린다.
- 한 파일 안에 같은 패턴이 30곳 이상 흩어져 있거나, 여러 파일에 걸쳐 영향 범위가 불명확한 경우는 파이프라인 대상이다.
- 공유 리소스(여러 화면이 참조하는 drawable/color 등)를 건드릴 때는 grep으로 참조처 수를 먼저 세고, 넓으면 범위를 좁히거나 짧게 확인만 받는다.

**Why:** 서브에이전트마다 몇 분씩 걸려 전체가 너무 느렸다. 사용자는 완벽한 사전 검증보다 속도를 원했고, 오류는 실기기에서 직접 찾겠다고 했다.

## 10. worktree는 요청할 때만

새 브랜치 작업도 별도 git worktree를 만들지 않고 메인 워크트리에서 `git switch`로 처리한다. 미커밋 변경과 충돌이 걱정되면 worktree를 만드는 대신 stash할지 커밋할지 사용자에게 묻는다.

**Why:** 미커밋 변경을 보호하려고 임의로 worktree를 만들었다가 "지정하지 않는 한 구분하지 말라"고 지적받았다.

## 11. 문서 수정 시 백업 파일을 만들지 않는다

이력서, 노트 같은 문서를 고칠 때 `.backup_*` 같은 복사본을 남기지 않는다. 원본만 고친다. 버전 관리가 필요하면 git이나 동기화 서비스의 기록을 쓴다.

**Why:** 매번 원본을 최신화하므로 백업은 쌓이기만 하고 쓰이지 않았다. 남은 백업을 전부 지우라는 지시를 받았다.

## 12. 인증 링크는 브라우저로 직접 연다

OAuth, MCP 인증, CLI 로그인처럼 사용자가 브라우저에서 승인해야 하는 URL은 채팅에 붙이는 것으로 끝내지 않는다. `open "<url>"`(macOS)로 기본 브라우저에 바로 띄우고, 채팅에는 "브라우저로 열어 두었다"와 리다이렉트 오류 시 대처만 짧게 적는다. URL 전문은 반복하지 않아도 된다.

**Why:** 긴 인증 URL이 터미널에서 잘려 사용자가 링크를 받지 못했다.

## 13. 같은 규칙을 기기 간에 공유하려면 저장소에 둔다

여러 기기에서 똑같이 적용돼야 하는 작업 규칙은 로컬 메모리에 두지 않고 해당 저장소의 규칙 파일(`AGENTS.md`/`CLAUDE.md`)에 둔다. 다른 프로젝트 세션에서 그 저장소 관련 작업(예: 블로그 글 쓰기)을 할 때는 해당 규칙 파일이 자동으로 로드되지 않으므로 작업 전에 직접 읽는다.

**Why:** 로컬 메모리는 기기별로 따로 저장돼서 다른 맥북에서 클론하면 규칙이 사라졌다.
