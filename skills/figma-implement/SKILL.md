## 목적

Figma 디자인(노드 링크) 또는 사용자가 캡처한 스크린샷을 실제 코드에 정확하게 반영한다.
**디자인이 유일한 진실 원천(SSOT)이고, 눈대중으로 "비슷하게" 맞추는 건 실패다.**

## 두 가지 입력 경로

### 경로 A: Figma 노드 링크가 주어진 경우

1. Figma MCP의 design-to-code 가이드(예: `figma-design-to-code` 스킬)를 먼저 로드하고, `get_design_context`로 정확한 스펙(spacing, 폰트 크기/lineHeight, 색상 토큰, corner radius, 아이콘)을 가져온다. `get_metadata`/`get_screenshot`만으로 대체하지 않는다.
2. **반환된 수치를 그대로 쓴다.** 스크린샷만 보고 눈대중으로 구현하지 않는다.
3. 부모/자식 컨테이너가 각자 padding을 가진 이중 구조("Header pb-10" + "Content pt-10" = 실제 간격 20dp)를 놓치지 않는다. 한쪽 padding만 보고 절반만 반영하는 실수가 잦다. 트리의 모든 조상 padding을 더해서 실제 간격을 계산한다.
4. 아래 "구현 규칙"을 따른다.

### 경로 B: 스크린샷만 주어진 경우 (Figma 링크 없음)

1. 스크린샷이 어느 화면/컴포넌트에 해당하는지 코드에서 먼저 찾는다(레이아웃 XML 또는 Composable, Activity/Fragment/Dialog).
2. **현재 구현과 스크린샷을 나란히 비교**해서 다음을 식별한다.
   - 새로 추가된 요소(현재 코드엔 없는 뷰)
   - 기존 요소의 변경 사항(텍스트/색상/크기/표시 조건 변화)
   - 제거된 요소
3. Figma 링크가 없으면 정확한 수치(hex, dp)를 알 수 없다. 이 경우:
   - 같은 화면이나 앱 안에 이미 확립된 같은 계열 컴포넌트의 기존 값(색상/폰트/간격)을 최대한 재사용해서 시각적으로 동일하게 맞춘다.
   - 참조할 기존 패턴이 없으면 프로젝트의 기존 그리드(4/8dp 배수 등)에 맞는 합리적 추정값으로 반영하되, **"정확한 스펙이 없어 추정값으로 반영했다"고 반드시 보고**한다.
   - 새 UI의 동작이나 트리거 조건이 스크린샷만으로 불명확하면 추측하지 말고 묻는다.

## 구현 규칙 (경로 A/B 공통)

### 1. 간격·타이포그래피

- Figma의 padding/margin/gap 값을 산술적으로 그대로 옮긴다.
- 폰트 크기/lineHeight는 Figma 값 그대로 쓴다.
- 텍스트 크기 단위(sp/dp)는 프로젝트 규칙 파일의 관례를 따른다.
- Figma가 요구하는 굵기(예: Medium)의 폰트 리소스가 프로젝트에 없으면(`res/font/`에 light/regular/bold만 있는 경우 등), 프로젝트의 기존 대체 관례(예: regular로 대체)를 확인해 따른다.
- 여러 줄(불릿 등)에 항목별 정확한 gap이 필요하면 단일 TextView + `\n\n` 대신 별도 TextView/컨테이너로 나눠 `layout_marginTop`으로 정확한 gap을 준다. `\n\n`은 줄바꿈 하나 분(약 1 lineHeight)을 추가해 Figma가 의도한 gap과 어긋나기 쉽다.

### 2. 색상/디자인 토큰: 프로토콜이 있으면 프로토콜, 없으면 정적 리소스

- 먼저 프로젝트에 다크/라이트나 테마를 런타임에 반영하는 색상 프로토콜(예: `ThemeColor` 객체, 테마 매니저)이 **실제로 존재하는지** 확인한다.
  ```bash
  grep -rln "object ThemeColor\|class ThemeColor" app/src/main/java --include="*.kt"
  ```
  브랜치마다 있을 수도 없을 수도 있다. 이전 세션 기억이나 다른 브랜치 경험으로 추측하지 말고 **현재 체크아웃된 브랜치에서 직접 확인**한다.
- 존재하면: Figma의 색상 토큰(예: `color-system/*`)을 그 프로토콜의 대응 프로퍼티로 매핑해 런타임에 적용한다.
- 존재하지 않으면: 정적 `@color/` 리소스로 매핑한다.
  - 먼저 `colors.xml`에서 Figma hex와 **정확히 일치하는 기존 색상**이 있는지 찾는다(예: `@color/danger` = `#FF4C30`이 Figma `status/danger/default`와 일치).
  - 없으면 새 색상을 추가하되, 알파가 있는 토큰(`rgba(r,g,b,a)`)은 `#AARRGGBB`로 정확히 환산한다. 예: `rgba(26,41,55,0.07)` → 알파 0.07×255≈18(0x12) → `#121A2937`.
- 토큰 대응이 애매하면 추측해서 매핑하지 말고 묻는다. 잘못된 매핑은 화면에 조용히 틀린 색이 들어가 발견하기 어렵다.

### 3. 공유 리소스는 함부로 고치지 않는다

- drawable/색상/치수가 다른 화면에서도 쓰이는지 먼저 확인한다.
  ```bash
  grep -rl "<대상 drawable/색상명>" app/src/main/res/layout app/src/main/java | wc -l
  ```
- 소비처가 지금 작업 중인 화면 한 곳뿐이면 자유롭게 고친다.
- 여러 화면이 공유하면 그 리소스를 직접 고치지 말고 **이 화면 전용 새 리소스**를 만들어 쓴다. 기존 공유 리소스와 스펙이 다르다는 사실은 사용자에게 보고하고, 전역으로 바꿀지 묻는다.

### 4. 아이콘은 이름만 보고 넘겨짚지 않는다

- Figma가 참조하는 아이콘(`Icon/System/Info Filled`, `Icon/System/Close Circle` 등)의 실제 svg path를 프로젝트 기존 drawable과 **path 내용으로 대조**해서 가장 가까운 것을 고른다. 이름이 비슷해도(`icon_error_filled` vs `icon_clear`) 실제 모양은 다르거나 같을 수 있다. 반드시 파일을 열어 확인한다.
- 새 아이콘을 손으로 그리지 않는다. 정확히 일치하는 기존 아이콘이 없으면 사용자에게 에셋을 요청한다.

### 5. 빌드 검증

빌드 태스크는 사용자가 요청한 경우에만 돌린다.

- XML/리소스만 바꿨으면: `./gradlew merge<Variant>Resources -q`
- Kotlin/Java도 바꿨으면: `./gradlew compile<Variant>Kotlin -q`
- 실기기 빌드/설치는 사용자가 명시적으로 요청할 때만 한다.
