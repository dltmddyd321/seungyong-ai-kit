# Android Test Pipeline

## 원칙

1. **순서를 지킨다: 요구사항 → 시나리오 → 테스트 → 구현.** 구현을 먼저 보고 거기에 맞춰 테스트를 쓰지 않는다. 그렇게 쓴 테스트는 요구사항이 아니라 구현을 확인할 뿐이다.
2. **사람이 정하고 AI가 반복한다.** 요구사항, 시나리오 승인, 코드 수정 승인, 최종 리뷰는 사용자 몫이다.
3. **behavior를 검증한다.** 내부 구현(private 호출 순서, 필드 값)이 아니라 입력에 대한 결과를 검증한다.
4. **많이 만들지 않는다.** 같은 behavior를 검증하는 테스트는 하나만 남긴다. 시나리오마다 "새로 보장하는 behavior"가 한 줄로 설명되지 않으면 뺀다.
5. **실패하면 멈춘다.** 자동으로 고치고 다시 돌리지 않는다. 한 번의 승인은 그 수정 한 건에만 유효하다.
6. **테스트를 통과시키려고 테스트를 고치지 않는다.** 테스트가 틀렸다고 판단되면 그 판단 자체를 보고하고 승인받는다.
7. **테스트는 Merge 후에도 남긴다.** 기능이 삭제되거나 요구사항이 바뀔 때만 수정하거나 삭제한다.

## 대상 우선순위

- 우선: 분기가 많은 순수 로직, 결제나 동기화처럼 틀리면 돈이나 데이터가 걸리는 로직, Coroutine/Flow 동시성
- 나중: ViewModel, Repository 주요 동작
- 최소화: UI/E2E. 핵심 사용자 시나리오만

## 작업 공간

`_workspace/test/{대상이름}/` 아래에 단계별 파일을 남긴다.

```
01_requirements.md   사용자가 정한 요구사항과 Business Rule
02_scenarios.md      승인된 테스트 시나리오
03_run_{N}.md        N번째 실행 결과 (실패 보고 포함)
04_summary.md        최종 결과
```

## Phase 1: 요구사항 확인 (사람)

1. 사용자에게 대상과 요구사항을 받는다. 요구사항이 없으면 코드를 읽고 "현재 코드가 하는 일"을 정리해 보여 주되, **그것이 올바른 요구사항인지 확인받는다.** 현재 동작이 곧 요구사항이라고 가정하지 않는다.
2. 대상 코드가 테스트 가능한 구조인지 본다. Activity, Context, DB 인스턴스, 싱글톤에 묶여 있으면 순수 함수나 주입 가능한 형태로 **분리할 범위를 먼저 제안**하고 승인받는다. 분리 자체도 코드 수정이다.
3. 결과를 `01_requirements.md`에 저장한다.

## Phase 2: 시나리오 초안 → 승인 (AI → 사람)

1. 요구사항마다 시나리오를 한 줄씩 뽑는다. 형식: `상황 → 기대 결과 (보장하는 behavior)`
2. 정상, 경계값, 실패, 동시성(해당 시) 순서로 정리하고 중복은 합친다.
3. **사용자에게 보여 주고 승인받는다.** 승인 전에는 테스트 코드를 쓰지 않는다.
4. 승인된 시나리오를 `02_scenarios.md`에 저장한다.

## Phase 3: 테스트 작성 (AI)

```
Agent(
  subagent_type: "android-test-writer",
  model: "sonnet",
  prompt: "_workspace/test/{대상}/02_scenarios.md의 승인된 시나리오만으로 테스트를 작성하라.
  대상: {클래스/함수 경로}
  프로젝트 루트: {PROJECT_ROOT}
  시나리오에 없는 테스트는 추가하지 마라. 작성한 파일 경로와 시나리오-테스트 대응표를 반환하라."
)
```

대상이 작아 파일 하나, 테스트 3~4개 수준이면 서브에이전트 없이 직접 작성한다.

## Phase 4: 실행 루프

```bash
cd {PROJECT_ROOT}
./gradlew compile<Variant>UnitTestKotlin
./gradlew test<Variant>UnitTest --tests "{테스트 클래스 FQN}"
```

- 새로 만든 테스트의 첫 실행은 **Red가 정상**이다. 구현이 아직 없거나 버그를 재현하는 테스트라면 실패해야 한다. 처음부터 통과하면 테스트가 아무것도 검증하지 않는지 의심하고 보고한다.
- 실행 결과는 매번 `03_run_{N}.md`에 저장한다.

### 실패 시: 즉시 멈추고 보고

아래 형식으로 보고하고 **사용자 응답을 기다린다.** 코드를 고치거나 다시 실행하지 않는다.

```
## 테스트 실패 보고 (실행 N회차)

- 단계: 컴파일 / 테스트 실행
- 실패 테스트: {클래스}.{테스트 이름}
- 위치: {파일}:{라인}
- 기대값: ...
- 실제값: ...
- 추정 원인: {코드 문제 | 테스트 문제 | 환경 문제} — 근거 한두 줄
- 제안 수정:
  - 대상 파일: ...
  - 변경 내용: ...
  - 테스트 코드 수정 여부: 예/아니오 (예라면 왜 테스트가 틀렸다고 보는지)
- 승인하시면 위 수정만 반영하고 처음부터 다시 실행합니다.
```

- 원인을 확신할 수 없으면 "확인 필요"로 적고, 확인에 필요한 정보(로그 추가, 재현 조건)를 제안한다. 추측을 사실처럼 쓰지 않는다.
- Red 단계에서 예상한 실패(구현 없음)는 보고만 하고 Phase 5로 넘어가도 되는지 묻는다.

### 승인 후

1. 승인받은 수정만 반영한다. 범위를 넓히지 않는다.
2. **처음부터 다시 실행한다.** 컴파일 → 대상 테스트 → 통과하면 전체 `./gradlew test<Variant>UnitTest`.
3. 다시 실패하면 같은 형식으로 보고하고 또 기다린다.

### 안전장치

- 같은 테스트가 3회 연속 같은 원인으로 실패하면, 수정 제안 대신 접근 자체를 다시 검토하자고 보고한다.
- 전체 테스트에서 이번 작업과 무관한 기존 테스트가 실패하면, 고치지 말고 따로 보고한다.

## Phase 5: 구현 (Green)

- 구현이 필요한 경우(신규 로직, 버그 수정)도 Phase 4와 같은 규칙을 따른다. 구현 계획을 먼저 보고하고 승인받은 뒤 작성한다.
- 규모가 크면 `android-dev` 스킬의 Implementer 흐름을 쓴다.

## Phase 6: 리팩터 제안 → 최종 리뷰 (AI → 사람)

1. 전체 테스트가 통과하면 리팩터 후보를 **제안만** 한다. 적용은 승인 후. 적용하면 처음부터 전체 테스트를 다시 돈다.
2. `04_summary.md`에 정리하고 사용자에게 보고한다.
   - 시나리오별 통과 여부
   - 추가하거나 수정한 파일
   - 테스트로 새로 보장하게 된 behavior 목록
   - 남은 위험이나 테스트하지 않은 부분
   - 커밋 메시지 제안

## 테스트 작성 규칙 (예시 구성, 프로젝트에 맞게 조정)

- 위치: `app/src/test/java/` 아래 대상과 같은 패키지
- 도구: JUnit 4, Truth(`assertThat`), mockito-kotlin. 가능하면 Mock보다 직접 만든 Fake
- 코루틴 테스트가 필요하면 `kotlinx-coroutines-test`가 있어야 한다. 의존성 추가는 먼저 승인받는다.
- 이름: 백틱 한글로 behavior를 쓴다. 예: `` `제목이 비어 있으면 저장 버튼이 비활성화된다` ``
- 주석을 달지 않는다.
- Android 프레임워크(Context, DB 인스턴스, Activity)가 필요한 테스트는 unit test로 쓰지 말고 분리를 먼저 제안한다.

## 빌드·테스트 실행 권한

이 스킬이 명시적으로 호출됐을 때만 Gradle을 실행한다. 다른 작업 중에 자동으로 테스트를 돌리지 않는다.
